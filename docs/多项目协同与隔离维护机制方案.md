## ✅ 可稳定达成效果

### 1. 核心原则：独立仓库维护，不混不合并

**DevProjectTeamSkill 可维护 dev-git-hub（及其他独立项目），但必须保持其完整独立**：

| 维度 | 规则 |
|------|------|
| **仓库边界** | 每个独立项目是**单独 git 仓库**（各自 .git/提交历史/远端），**不子模块嵌套、不 symlink 共享源** |
| **内容边界** | 维护独立项目时，改动**只落独立项目仓库**，不写入本项目；本项目的维护动作（审计/台账/断点）记录在本项目 |
| **工作目录** | 维护动作以**独立项目根为工作目录**（`cd dev-git-hub`），本项目经「独立仓库 + 引用登记 + 交叉调用」协同 |
| **共享标准** | 治理/审计/脱敏等**跨项目标准经 references/ 引用**（不入独立项目复制）；独立项目私有实现各自维护 |

> **证据**：EV-503[high]（polyrepo 标准：多仓库各自版本/依赖/CI，不合并）、EV-502[high]（dev-git-hub 已独立）、EV-504[medium]（项目组合：协同经引用非合并）

### 2. 多项目协同机制（跨项目层面）

| 协同点 | 机制 |
|--------|------|
| **引用登记** | 独立项目在本项目登记（AGENTS.md 或 references）：路径/授权/用途——本项目用 `references/项目清单` 登记，不复制内容 |
| **交叉调用** | 独立项目能力经**工具调用**（薄封装代理/CLI），本项目仅转发（dev-git-hub 已有薄封装代理先例） |
| **治理协同** | 跨项目依赖/里程碑/统一标准 → `role-program-mgmt`（项目群协同已具备）；独立项目治理留其在各仓库 |
| **审计协同** | 独立项目维护操作留痕在本项目 13/14 台账（操作方注明 dev-git-hub）；独立项目内部留痕在各自台账 |

### 3. 维护流程（本项目维护独立项目的标准动作）

```bash
# 维护 dev-git-hub（例）——改动只落独立仓库
cd /Volumes/BR256G/dev-git-hub        # 工作目录=独立项目根
# ... 改代码 ...
git add -A && git commit              # 提交到 dev-git-hub 仓库
git push hub main                     # 推 dev-git-hub LAN 中枢 + origin/mirror
# 本项目只登记维护动作（13/14 台账 + 交接待办），不复制 dev-git-hub 内容
```

### 4. 隔离原则（与 multi_project_isolation 5 层对齐）

- **Git 层**：独立仓库互相独立（不混提交历史）
- **配置层**：各自 .gitignore（dev-git-hub 已隔离 config.yaml/.secrets/台账）
- **服务层**：各自端口/资源注册（25_环境资源清单 全局注册，冲突升阶）
- **治理层**：独立项目各自评审/门禁；跨项目走 role-program-mgmt

> **证据**：EV-501[high]（现成 5 层隔离框架）、EV-502[high]（dev-git-hub 已隔离敏感）

## ⚠️ 理论最优效果与当前限制

| 限制/反信号 | 说明 | 缓解 |
|-------------|------|------|
| 独立项目共享代码过多 | 若跨仓库共享实现增多 → 考虑公共库/子模块 | 反信号：共享度超阈值时评估；缺省「引用优于复制」 |
| 隔离过严维护成本高 | 独立项目各自发布/门禁 → 重复成本 | 复用本项目发布/审计工具（薄封装调用），非另起一套 |
| 维护动作分散两仓库 | 本项目登记 + 独立项目提交，可能漏登记 | 维护动作完成即本项目审计留痕（铁律#7b 四维定位） |

## 决策记录草案

- **标识**：ADR-2026-08-30-002（待架构角色正式编号）
- **决策**：本项目以「独立仓库 + 引用登记 + 交叉调用」模式维护 dev-git-hub 等独立项目——**不混不合并**，保持各项目完整性与独立性；共享标准引用不复制
- **选项**：
  - A. 子模块/嵌套合并 → ❌ 破坏独立性、耦合两仓库
  - B. **独立仓库 + 引用协同（本方案）** → ✅ polyrepo 标准、防膨胀、可演进
  - C. 彻底隔离无协同 → ⚠️ 无法复用标准/工具，维护成本高
  - D. 合并入本项目 → ❌ 膨胀+耦合，违反本项目定位
- **理由**：EV-501/502/503/504 证据链
- **已验证**：dev-git-hub 已独立仓库（三远端+隔离）；multi_project_isolation 与 role-program-mgmt 现成
- **不确定**：维护频率/共享度阈值需实测校准
- **未关闭风险**：维护动作分散两仓库的漏登记风险（铁律#7b 四维定位缓解）
- **反信号**：共享代码增多 → 评估公共库；隔离成本高 → 合并评估
